# Sunday 插件开发手册

本手册对应当前的 `core/core.py` 架构；旧版 `sun_cli.py` 时代的规则已废弃。

---

## 一、运行模型

```text
sun (短命客户端)
  → 连接 core/core.sock
  → 发送指令
  ← 收到输出并退出

core/core.py --daemon (常驻)
  → G / T 不存在就创建
  → 挂载 log / init / server 三件套
  → init 读取 core/init.json 与模块 JSON, 初始化 used && init 的模块
     初始化 = G.<模块> = 实例 + 调用模块的 init()
  → 阻塞监听，串行处理指令
  → 退出或收到信号: init.shutdown() + server.shutdown()
```

`log` / `init` / `server` 是 `core/` 里的内置工具，不是插件：`log` 支撑 `G.log`，`init` 读取 `core/init.json` 决定初始化哪些模块，`server` 提供 `G.server`。它们始终随 core 启动。

常用命令：

```bash
sun                    # 确保 core 运行(不在则拉起, 已在运行则重启)
sun stop               # 停止 core
sun help               # 显示帮助和模块列表
sun list               # 只列出各模块 name
sun init [模块...]     # 按模块 JSON 的 init 初始化, 或初始化指定模块
sun <role>             # 调用模块的 run(); name 也可作为别名
sun <role> <子命令>     # 调用模块 subcommands 中登记的方法
```

`core` 只在第一次 `sun` 时自动拉起；之后一直常驻。`core` 退出后，下一次 `sun` 会重新拉起它。

## 二、目录规范

```text
modules/
└── mymodule/
    ├── mymodule.py      # core 唯一加载目标
    ├── mymodule.json    # 与 py 同名的市场元数据; core 读取 ID
    └── assets/          # 模块自己的资源, core 不加载
```

规则：

- core 只扫描 `modules/*/` 这一层目录。
- 目录名以 `_` 开头的模块会被跳过（可用来临时禁用或存放素材）。
- 只加载 `modules/<目录名>/<目录名>.py`。
- 同目录下的其他文件不会自动加载。
- 需要常驻进程的模块可以再加一个独立入口 `serve.py`（见 §九），它不依赖 core 注入的 `G` / `T`。
- 如果模块需要同目录的辅助 `.py`，可以用项目根作为路标导入，例如：

```python
from modules.mymodule import helper
```

core 以项目根为启动目录，项目根在 `sys.path` 中，所以这种导入方式可用。

- 目标文件固定导出名为 `Module` 的类：

```python
class Module:
    ...
```

core 只认 `Module`，不再用 `inspect` 猜“第一个类”。

## 三、最小模块

```python
class Module:
    role = "mymodule"                 # 主键, 必填, 非空字符串
    name = "mymodule"                 # 可选别名; 省略时等于 role
    desc = "一句话描述"                # sun help 显示
    used = True                       # 是否出现在 sun help / 允许 sun <role> 调用
    subcommands = ["status", "help"]  # 可通过 CLI 调用的子命令(list[str])

    def init(self):
        """可选: core 初始化时调用; 必须快速返回"""
        pass

    def shutdown(self):
        """可选: core 退出或收到关闭信号时调用"""
        pass

    def run(self):
        """sun mymodule: 无子命令时调用"""
        print("mymodule run")

    def status(self):
        """sun mymodule status: 子命令"""
        print("ok")

    def help(self):
        """sun mymodule help"""
        print(self.desc)
```

ID 放在同目录与模块同名的 `mymodule.json` 里（`name`、`role`、`desc`、`used`、`init` 也可以写进去）：

```json
{
    "name": "mymodule",
    "role": "mymodule",
    "desc": "一句话描述",
    "ID": "mymodule1792906494",
    "used": true,
    "init": false,
    "依赖": [],
    "依赖模块": []
}
```

> 旧模块可能把 `ID` 写在类属性里；core 在没有 JSON `ID` 时用它兜底。新模块统一写在 JSON。

### 生命周期

1. core 扫描 `modules/*/`，只读 manifest 建立索引，不导入模块。
2. `init` 工具读取 `core/init.json` 的模块列表与顺序，再按各模块 JSON 的 `init` 选出 `used && init` 为真的模块。
3. 按列表顺序导入目标文件、实例化 `Module`，挂载 `G.<name>` / `G.<role>`。
4. 发现同 role 模块时，用 `ID` 时间戳比较，大的替换旧的。
5. 调用模块的 `init()`；失败写 `G.log`，继续下一个。
6. 进入命令循环；其他模块第一次被 `sun` 调用时才导入，不自动初始化。
7. 退出或收到 SIGINT / SIGTERM / SIGHUP 时，`init.shutdown()` 逆序调用模块可选的 `shutdown()`，`server.shutdown()` 停止托管进程。

注意：

- `Module` 必须是类，构造函数必须无参。
- `role` **必填**，必须是非空字符串。
- `name` 是可选的 CLI 别名；省略时等于 `role`。
- `used` 可选，默认 `True`。可以写在模块类里、`<名字>.json` 里或 `core/init.json` 里；`init.json` 优先。设为 `False` 时，模块不会出现在 `sun help`，也不能用 `sun <role>` 调用，并且不会被初始化。
- `init` 写在 `<名字>.json` 里，默认 `False`；为 `True` 且 `core/init.json` 中 `used=True` 时，core 启动会调用模块的 `init()`。`market` 安装模块时会把该值写入 `core/init.json`。
- `desc`、`subcommands` 可以省略，core 会使用默认值。
- `init()` 可选，只在 core 启动且模块 JSON 的 `init=true`、`core/init.json` 中 `used=true` 时调用；必须快速返回，不能阻塞。进程类模块（`lobo`、`whiteblob`）在 `__init__` 挂载时完成 `G.server.register`，`init()` 里直接调用 `run()` 启动服务。
- `init()` 抛异常：`init` 工具写入 `G.log`，并把模块移出列表。
- `init()` 按 `init.json` 的列表顺序串行执行；模块间有初始化依赖时，把被依赖的模块写在前面。
- `sun <模块> <子命令>` 不会自动补初始化：模块未初始化时只按需导入并直接执行；如果模块 JSON 的 `init=true` 且 `core/init.json` 要求它必须初始化，则提示“模块 X 未初始化”。
- `shutdown()` 可选，core 退出或收到关闭信号时逆序调用。
- `load()` / `start()` 不再有生命周期含义，这两个名字已经空出来，可以当作普通方法名或子命令使用。
- 模块在 core 进程内只导入一次。改完代码后需要重启 core。

重启方式：

```bash
sun stop
sun <role> ...
```

## 四、命令路由

```bash
sun mymodule                 # 调用 run()
sun mymodule status          # 调用 status()
sun mymodule status a b      # 调用 status("a", "b")
```

规则：

- `run` 只在**没有子命令**时调用，不要在 `run` 里堆子命令解析。
- 每个子命令写成一个同名方法，并登记到 `subcommands` 列表。
- 只有 `subcommands` 中登记的方法可以通过 CLI 调用。
- `run` 是默认入口，不需要放进 `subcommands`。
- core 在模块加载或初始化时会校验列表：不存在或不可调用的名字会跳过。
- 子命令不存在时直接报错，并列出当前可用子命令，不会回退到 `run`。
- 方法返回值不会自动打印；需要输出时使用 `print()`。

示例：

```python
class Module:
    role = "mymodule"
    name = "mymodule"
    subcommands = ["status", "help"]

    def run(self):
        print("default")

    def status(self):
        print("ok")

    def help(self):
        print("help")
```

```bash
sun mymodule                 # run()
sun mymodule status          # status()
sun mymodule status a b      # status("a", "b")
sun mymodule nope            # 报错, 并列出可用子命令
```

### 一次带子命令的调用：`sun whiteblob help`

1. `sun` 客户端把参数原样发给 core：`["whiteblob", "help"]`
2. core 用第一个参数 `whiteblob` 先查 `role`、再查 `name`（`whiteblob` 是 name，role 是 `gui`）
3. 找到模块后，把剩余参数 `["help"]` 当作子命令
4. 检查 `"help"` 是否在模块的 `subcommands` 列表里
5. 通过后调用 `module.help()`
6. `print()` 的输出被 core 捕获，随响应返回给 `sun`

注意区分：

```bash
sun help            # core 内建帮助
sun whiteblob help  # 穿透给 whiteblob 模块的 help()
sun market help     # 穿透给市场模块的 help()
```

仓库里的 `modules/example/` 只用来给开发者看结构和接口写法，不是可运行示例：它 `used = False`，并且 `init()` 里会把自己从 `G.MODULES_LIST` 移除，所以 `sun example help` 不存在。想本地验证它，删掉 `init()` 里那行、把 `used` 改成 `True`，再 `sun stop` 重启即可。

`help` 是 core 内建命令，只输出全局帮助和模块列表，不接受模块名参数；同 role 模块无法覆盖它。`list` 也是 core 内建命令，只打印可用指令列表，不含用法说明；模块不能占用这两个 role/name。

模块自己的子命令仍可以叫 `list`（例如 `sun market list`），保留的只是顶层 `sun list`：

```bash
sun mymodule list
```

### help 输出

`sun help` 只打印全局用法和模块列表，每个模块一行；只想看可用指令时用 `sun list`，它只打印各模块的 name，不含标题、用法和说明：

```text
market / market_manager  - 模块市场管理器: ...
```

core 不解析 docstring，也不列子命令。模块自己的说明由模块的 `help` 子命令提供（可选，但建议写）：

```python
class Module:
    role = "market"
    desc = "本地模块市场"
    subcommands = ["help", "list"]

    def help(self):
        print(self.desc)
        print("用法:")
        print(f"  sun {self.role} list")
```

实际效果参考 `sun market help`、`sun whiteblob help`。

## 五、G 与 T

core 在导入模块文件之前，会把 `G`、`T` 注入模块的全局命名空间：

```python
def init(self):
    print(G.APP_PATH)
    print(T.CLIENT_CWD)
```

不要写 `class Module(G, T)`，也不要 `from core import G`。它们是注入的实例，不是基类。

### G：全局共享对象

| 属性/方法 | 说明 |
| --- | --- |
| `G.APP_PATH` | 项目根目录 |
| `G.MODULES_LIST` | 已导入的模块实例列表；初始化过的模块会出现在里面 |
| `G.by_name` | `name -> 模块实例` 别名索引 |
| `G.by_role` | `role -> 模块实例` 主键索引 |
| `G.get(name, default=None)` | 按 role 或 name 取模块，找不到返回 `default`；role 优先 |
| `G.call(*argv)` | 在 core 内执行一条 sun 指令，返回 `(code, stdout, stderr)`；例如 `G.call("lobo", "get")`，不启动子进程 |
| `G.server` | 由 core 的 `server` 工具提供，始终可用：`register(name, argv, marker="", env=None)` / `start` / `stop` / `status` / `list` / `identity()`；`env` 是额外的环境变量 dict |
| `G.init` | core 的 `init` 工具：`load()` / `save(entries)` / `ensure(token)` / `set(token, used, init)` / `remove(token)`，用于读写 `core/init.json` |
| `G.log(message, path="")` | 追加一条带时间戳的日志；`path` 为空时写入 `./log/sun.log` |
| `G.<name>` / `G.<role>` | 只有初始化过的模块才会挂载；前提是名字是合法标识符且不与 core 保留名冲突 |

查找顺序是 **role 优先，name 兜底**。模块间取实例时优先用 `G.get("xxx")` 或 `G.xxx`，不要直接依赖 `G.by_name` / `G.by_role` 处理冲突。

需要按 CLI 语义调用其他模块（子命令校验、初始化策略、输出捕获）时用 `G.call`：

```python
code, out, err = G.call("lobo", "get")
if code == 0:
    print(out)
```

`G.call` 与 `sun lobo get` 走同一套路由，返回客户端会拿到的 `code / stdout / stderr`；它不会重新启动 `sun` 进程。

`G.log` 的第二个参数可以是绝对路径，也可以是相对项目根目录的路径：

```python
G.log("mymodule 启动完成")                    # 写入 ./log/sun.log
G.log("下载失败", "log/download.log")          # 写入项目根下的 log/download.log
G.log("使用绝对路径", "/tmp/mymodule.log")     # 写入指定文件
```

写入格式为：

```text
[2026-10-25 14:30:00] mymodule 启动完成
```

不要假设某个模块一定存在。插件之间应该是可选依赖。

### T：请求上下文

| 属性 | 说明 |
| --- | --- |
| `T.CLIENT_CWD` | 本次 `sun` 调用时用户所在目录 |

`T` 只用于临时上下文，不要在里面保存跨请求的长期状态。

## 六、name、role 与 ID

### role

- **主键，必填，非空字符串**。
- 不支持列表、`None` 或空字符串。
- 未设置 `role` 的模块会被丢弃。
- 例如：

```python
role = "log"
name = "mylog"    # 可选别名
```

这样 `sun log` 是主命令，`sun mylog` 也能命中。

### name

- 可选的 CLI 别名。
- 省略或为空时自动使用 `role`。
- 查找顺序：先查 `role`，没有命中才查 `name`。

### used

- 可选布尔值，默认 `True`。
- 可以写在模块类里、`<名字>.json` 里或 `core/init.json` 里；优先级 `init.json` > `<名字>.json` > 类属性。
- `used = True`：模块出现在 `sun help`，允许 `sun <role>` 调用，并可能被初始化。
- `used = False`：模块不出现、不可调用、不会被初始化。
- 如果模块需要一个叫 `used` 的子命令（例如 `market used`），不要在类里声明 `used` 布尔属性，改用 JSON 的 `"used"` 字段。core 内部最终状态保存在 `_used`。
- `market used/unused` 会同时修改 `<名字>.json` 和 `core/init.json`。

### ID

- ID 写在同目录的 `<名字>.json` 里；`sun market mkid <name>` 会生成 `name + str(int(time.time()))` 的新 ID，也可以手写。
- 例如：

```json
{"ID": "myplugin1792906494"}
```

- core 优先用 JSON 的 `ID`；没有 JSON `ID` 时用类属性 `ID` 兜底（兼容旧模块）。
- core 读取 manifest 后，去掉 `name` / `role` 前缀，把剩余数字按整数比较。
- 发现同 role 模块时，ID 时间戳大的直接替换旧的。
- 没有 ID 或数字解析失败时视为最小；同 role 且时间戳不更大时保留旧模块。
- 不需要 `priority` 字段。

## 七、`<名字>.json`

`modules/<名字>/<名字>.json` 是市场/开发者元数据。core 会读取 `ID`、`used`、`init` 和 `desc`（`desc` 缺失时用 `help` 兜底），其余字段不由 core 使用。

示例：

```json
{
    "name": "mymodule",
    "role": "mymodule",
    "desc": "一句话描述",
    "ID": "mymodule1792906494",
    "used": true,
    "init": false,
    "依赖": ["Pillow>=10.0.0", "opencv-python"],
    "依赖模块": ["gui"],
    "api": ["print(text, duration=3000)", "add_button(text, command=\"\")"]
}
```

说明：

- `ID` 用于同 role 模块的时间戳比较和替换。
- `used` 控制是否出现在 `sun help`、是否允许 `sun <role>` 调用；`core/init.json` 里的同 name 条目优先。
- `init` 控制是否随 core 启动初始化：为 `true` 且 `core/init.json` 中 `used=true` 时，core 启动会调用模块的 `init()`；`market` 安装模块时会把该值写入 `core/init.json`。当前只有 `lobo` 和 `whiteblob` 为 `true`。
- `desc` 可作为模块 `desc` 的兜底；`help` 是兼容旧字段。
- `api` 是模块对外提供的**程序接口**清单（写给别人看的，可带签名），不是 CLI 子命令；core 和 market 系列都不读它，CLI 子命令以模块类的 `subcommands` 为准。
- `依赖` 是 python 包依赖列表，写法和 `requirements.txt` 一致（可带版本约束）；`sun market auto`（`market_manager` 同样可用）会检查并按需安装。
- `依赖模块` 是需要先安装/先初始化的模块 role 列表；`sun market auto` 会把已安装的依赖模块在 `core/init.json` 中移到依赖它的模块前面，未安装时只提示用 `sun market find <role>` 查找。
- 模块需要读取自己的完整配置时，自己读：

```python
import json
from pathlib import Path

cfg = json.loads(Path(__file__).with_suffix(".json").read_text("utf-8"))
```

## 八、输出、日志与错误

### 输出

`print()` 会被 core 捕获，并随命令结果返回给 `sun`：

```python
def status(self):
    print("ok")
```

后台线程里的 `print()` 不保证能被当前请求捕获，长期运行的服务应写日志或走自己的控制通道。

### 日志

core 自身只对致命错误写 `core/core.log`：

- 追加一条 fatal 记录到 `core/core.log`
- 调用系统消息弹窗：Windows `MessageBox`、macOS `osascript`、Linux `zenity` / `kdialog` / `notify-send`
- 没有可用 GUI 工具时回退到 stderr

注意：daemon 的 stdout/stderr 也重定向到 `core/core.log`，所以模块在导入或 `init()` 阶段直接 `print()` 的内容会出现在这个文件里；命令执行期间的 `print()` 由 core 捕获回传给 `sun`。

模块自己的常规输出用 `print()`；需要写日志时直接用 core 提供的 `G.log`：

```python
G.log("mymodule: something happened")
G.log("mymodule: 写入自定义文件", "log/mymodule.log")
```

默认写入项目根目录下的 `log/sun.log`。`G.log` 会自动创建父目录，并按追加方式写入。

### 错误

- 未知模块 / 未知子命令：返回错误，退出码 2。
- 模块方法抛异常：core 把 traceback 返回给 `sun`，退出码 1。
- `init()` 失败：写入 `G.log`，模块不会进入已初始化集合。
- 模块未初始化但 `init.json` 要求初始化：提示“模块 X 未初始化”，退出码 2。
- core 自身无法继续运行：fatal 日志 + 系统弹窗。
- 需要用户确认的危险操作可以 `raise SystemExit(3)`：`sun` 会提示“输入 y 确认，直接回车取消”，输入 `y` 后用原参数加 `--yes` 重发；模块看到 `--yes` 直接执行。
- 通过 `G.call` 调用其他模块时不会弹确认提示，退出码 3 会直接返回给调用方，由调用方决定如何处理。

## 九、长任务与常驻服务

core 是**单线程、串行**处理命令的：

- `init()` 必须快速返回。
- `run()` 或子命令如果阻塞，会挡住其他所有 `sun` 命令。
- 长任务请自己开线程/进程，或提供自己的控制通道。
- `server` 工具负责拉起、查状态、停止 `G.server` 登记的进程，不做崩溃重启。

推荐模式（窗口/服务类模块）——**facade + 独立服务进程**：

```python
# modules/ui/ui.py —— core 侧 facade, 只做声明和代理
class Module:
    role = "ui"

    def __init__(self):
        # 挂载时登记, 不启动
        G.server.register(
            "ui",
            [sys.executable, "-m", "modules.ui.serve"],
            marker="modules.ui.serve",
        )

    def init(self):
        # core 初始化时直接启动服务
        self.run()

    def run(self):
        G.server.start("ui")
        if not G.server.wait("ui", timeout=5, probe=...):
            print("ui 启动失败")

    def stop(self):
        G.server.stop("ui")
```

```python
# modules/ui/serve.py —— 独立程序, 自己初始化
if __name__ == "__main__":
    main()
```

- 服务进程用独立入口（`python -m modules.<名字>.serve`），不要再通过 core 启动；`server` 工具只负责拉起、查状态、停止。
- core 启动时只挂载 facade，服务注册放在 `__init__`（挂载阶段）；需要随 core 启动的服务，在 `init()` 里直接调用 `run()` 拉起。`serve.py` 不依赖 core 注入的 `G` / `T`：路径用 `Path(__file__).resolve().parents[2]` 自己算，日志直接 `print`（core 会把服务 stdout/stderr 重定向到 `core/services/<名字>.log`）。
- `G.server.start(name)` 只保证进程已创建；就绪用 `G.server.wait(name, timeout, probe)` 探测（socket 能连、HTTP 健康检查能回），探测失败时把 `core/services/<名字>.log` 尾部打给用户。
- `G.server.register(..., persist=False)` 默认随 core 一起停止（`sun stop`、关闭信号和 core 退出清理都适用）；`persist=True` 的进程在 core 退出时保留，下次 core 启动时按 PID 接管。
- `G.server` 由 core 的 `server` 工具提供，始终可用。
- PID 与日志统一在 `core/services/<名字>.pid|log`。
- 进程需要接收运行时指令时，起自己的本地 socket（`data/services/` 下）或 HTTP，不要依赖 core 的 stdin/stdout。
- 参考实现：`modules/whiteblob/`（`whiteblob.py` facade + `serve.py` 窗口进程 + `common.py` 共享常量）。

### GUI 工具面板按钮（whiteblob）

窗口进程把按钮保存在 `_GuiApp.buttons` 列表，右键（`<Button-3>`）打开工具面板，`_render_tools()` 负责渲染。每项是 `(显示文字, sun 命令)`，点击后由窗口进程执行 `sun <命令>`。

其他模块通过 facade 写入，推荐在 `init()` 里注册：

```python
def init(self):
    """向 GUI 注册快捷按钮; 失败只记录日志"""
    try:
        gui = G.get("gui")
        if gui is None or not gui.add_button("豆包", "doubao"):
            raise RuntimeError("gui 未运行")
    except Exception as exc:
        G.log(f"doubao 注册按钮失败: {exc}")
```

规则：

- 模块 JSON 的 `依赖模块` 加上 `"gui"`，保证 gui 先安装、先初始化（窗口进程先启动）。
- `command` 写不带 `sun` 的命令字符串，例如 `"lobo get"`；点击后窗口进程执行 `sun lobo get`。
- `gui.add_button(text, command)` 返回是否送达；`gui.create_btn(...)` 是带输出的 CLI 包装。
- 按钮只存在窗口进程内存里，core 或 GUI 重启后由模块的 `init()` 重新注册，所以注册必须允许失败，用 `G.log` 记录后继续。
- 参考实现：`modules/lobo/lobo.py` 的 `_register_buttons()`；按钮接口本身在 `modules/whiteblob/whiteblob.py` 的 `add_button()`。

## 十一、调试

```bash
sun                       # 确保 core 运行(已在运行则重启)
sun stop                  # 停止 core
sun help                  # 看模块有没有加载
tail -f core/core.log     # 致命错误; 模块导入/init() 的输出也会落在这里
tail -f log/sun.log       # 看 G.log 写入的模块日志
sun <role> ...            # 下一次会自动拉起 core
```

模块没出现时，按顺序检查：

1. 目录是否是 `modules/<名字>/<名字>.py`；
2. 目标文件是否导出了名为 `Module` 的类；
3. `init()` 是否抛异常（失败会写入 `G.log`）；
4. `init()` 是否把自己从 `G.MODULES_LIST` 移除了；
5. `used` 是否在模块 JSON 或 `core/init.json` 里被设成了 `False`；
6. core 是否需要重启（模块代码只在进程内导入一次）。

## 十二、注意事项

1. **不要继承 G/T**，它们是注入实例。
2. **不要 `from core import G`**；二次导入拿到的是类，不是 core 注入的实例，直接用注入的 `G`。
3. **不要在 `run()` 里堆子命令解析**，子命令写成同名方法并登记到 `subcommands`。
4. **`role` 必填且是非空字符串**；`name` 只是可选别名。`role` 是 `help` / `stop` 时模块会被丢弃；`name` 是保留字时会自动退回 `role`。
5. **不要假设其他模块存在**，用 `getattr(G, "...", None)`。
6. **不要在 `init()` 里阻塞**。
7. **同目录的辅助文件不会被自动加载**，需要模块自己处理。
8. **`<名字>.json` 的 `ID` 由 core 用于同 role 替换；`依赖`、`依赖模块`、`api` 不由 core 使用**。
9. **模块在进程内只导入一次**，`init()` 由 core 的 `init` 工具调度；改代码后重启 core。
10. **`help` / `list` / `stop` / `init` 是 core 保留命令**；模块不能占用这些 role/name（`name` 是保留字时会退回 `role`），但模块子命令可以叫 `list`。
11. **core 当前是 Linux 优先的 UDS 实现**；插件不需要关心传输层，但跨平台运行 core 前需要确认目标系统支持。
12. **core 只对致命错误弹系统消息**；`init()` 失败会写入 `G.log`，模块 import 失败仍会被静默跳过。
13. **辅助文件用 `from modules.<目录名> import <模块>` 导入**，不要依赖模块目录被加入 `sys.path`。
14. **模块未初始化也可以被调用**：`sun <模块>` 会按需导入后直接执行，不会自动补 `init()`。
15. **`load()` / `start()` 不再有生命周期含义**，core 不会调用它们；需要隐藏模块请设 `used = False`。
16. **初始化由模块 JSON 的 `init` 决定**：`core/init.json` 提供模块列表和顺序，`used && init` 才会在启动时初始化；`market` 安装、启用、删除模块时会自动维护。

## 十三、market / market_manager 模块

市场有两个模块，`role` 都是 `market`；同时存在时按 ID 时间戳只加载一个：

| 模块 | 面向 | 功能 |
| --- | --- | --- |
| `market` | 用户（发布版） | 查询、安装、依赖检查和本地管理 |
| `market_manager` | 开发者 | 上述全部 + 上传、删除云端 |

- 开发本仓库时先 `sun market install market_manager`；它的配置在 `modules/market_manager/market_manager.json`。
- 面向用户的发布版用 `market`（配置在 `modules/market/market.json`），用户拉下项目即可使用。
- 本地不必同时保留两个；只要模块代码不改，用哪个都行。只想验证发布版时，可把 `modules/market_manager` 目录临时改名（如 `_market_manager`），core 会跳过 `_` 开头的目录；验证完改回并重启 core。

`role` 相同，所以 `sun market ...` 和 `sun market_manager ...` 都能命中当前加载的那个：

```bash
sun market_manager list                 # 列出已安装模块
sun market_manager find <关键词>        # 搜索共享 Release
sun market_manager find_all             # 列出共享 Release 中所有模块
sun market_manager auto                 # 检查依赖并整理初始化顺序
sun market_manager install <name/ID>    # 安装或更新模块
sun market_manager mkid <name/ID>       # 生成或更新 ID
sun market_manager used <name/ID>       # 启用模块
sun market_manager unused <name/ID>     # 弃用模块
sun market_manager rm <name/ID>         # 删除本地模块目录
sun market_manager upload <name/ID>     # 上传模块 zip(仅 market_manager)
sun market_manager delete <name/ID>     # 删除云端模块(仅 market_manager, 需确认)
```

发布版 `market` 没有 `upload` / `delete`，其余命令与上表一致；把命令里的 `market_manager` 换成 `market` 即可。安装、删除等二次确认统一为输入 `y` 继续，直接回车取消。

只想读代码、不想启用某个模块：执行 `sun market unused <name>`，它会同时修改 `<名字>.json` 和 `core/init.json`。模块不出现在 `sun help`，不能用 `sun <role>` 调用，也不会被初始化。仓库里的 `example` 就是这么做的。

### 配置

两个模块各自读同目录 `<名字>.json` 的 `gitee` 字段。发布版只需要：

```json
{
    "gitee": {
        "repo": "xiuufa/sunday",
        "release_tag": "mods",
        "index_asset": "index.json"
    }
}
```

`market_manager` 额外支持 `token`、`release_name`、`target_commitish`：

```json
{
    "gitee": {
        "repo": "xiuufa/sunday",
        "token": "",
        "release_tag": "mods",
        "release_name": "Sunday modules",
        "target_commitish": "master",
        "index_asset": "index.json"
    }
}
```

- `repo` 写 `owner/repo`，也可以直接写 Gitee 地址。
- download 读取公开仓库，不需要 token。
- upload / delete 需要 token：`GITEE_TOKEN` 环境变量、`env:GITEE_TOKEN`、直接填 `gitee.token`，或保存到 `~/.config/sunday/gitee_token`。
- 不要把真实 token 提交到仓库。
- `target_commitish` 是创建 Release 时使用的分支，默认 `master`。

### 共享 Release

- 所有模块共用一个 Gitee Release：`tag = mods`。
- 每个版本保存为 `<ID>.zip`，旧版本不删除。
- 额外维护一个 `index.json`，记录所有版本的 `name`、`role`、`ID`、`desc`、`asset`、`download_url`。
- `find` 只读取 `index.json`，不会下载所有 zip。
- 同 `name` 在展示时只显示最新 ID，但云端保留所有版本。
- 同一个 ID 不允许重复上传；需要新版本时先 `sun market mkid <name>`。
- `find` / `install` 会把 `index.json` 缓存到项目根目录 `tmp/index.json`；该目录由市场模块在启动时清空。

### 行为

- `list` 扫描 `modules/*/`，读取每个模块的 JSON 和已加载实例，同 `name` 只显示最新 ID。
- `find` 在 `index.json` 中按 `name`、`role`、`ID`、`desc` 做大小写不敏感匹配，同 `name` 只显示最新；云端失败时可回退到本地缓存。
- `find_all` 不做关键词过滤，按 `name` 列出 `index.json` 中的全部模块；同样支持缓存回退。
- `auto` 先记录所有本地模块的 `role`，再逐个读取模块 JSON：`依赖` 缺失时询问是否 `pip install`；`依赖模块` 已安装时把它在 `core/init.json` 中移到依赖它的模块前面，未安装时只提示 `sun market find <role>`。
- `install` 按 name 或 ID 从 Gitee Release 下载 zip，校验包内 `name`、`ID` 和路径后安装到 `modules/<name>/`；已存在时先备份再替换。要移除的旧 ID 不在云端时，客户端会要求输入 `y` 确认；也可以直接加 `--yes`。
- `mkid` 写入 `<name><int(time.time())>`；重启 core 后参与同 role 替换。
- `upload`（market_manager）检查 ID 必须是 `<name><数字>`，并拒绝云端已存在的同 ID；打包整个模块目录，并清空自身 zip 里的 token。
- `delete`（market_manager）按 ID 精确删除；传入 name 时删除该 name 的全部云端版本。删除 zip 资产并重写 `index.json`，执行前需要输入 `y` 确认。
- `used` / `unused` 写入目标模块 JSON 的 `used` 字段；已加载模块会立即同步，重启后依然保持。
- `install` 成功后把模块的 `role`（没有时用 `name`）追加到 `core/init.json` 的初始化列表，并自动执行一次 `auto` 检查依赖、整理初始化顺序。
- `rm` 删除目标模块目录，并从当前 core 的 `G.MODULES_LIST` 和索引中移除；同 role 还有别的模块时保留 `init.json` 条目。
