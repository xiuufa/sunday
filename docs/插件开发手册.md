# Sunday 插件开发手册

本手册对应新的 `core.py` 架构。旧版 `mudels/`、`sun_cli.py` 的规则已废弃。

---

## 一、运行模型

```text
sun (短命客户端)
  → 连接 core/core.sock
  → 发送指令
  ← 收到输出并退出

core.py --daemon (常驻)
  → 启动时加载全部插件并初始化一次
  → 阻塞监听，串行处理指令
```

常用命令：

```bash
sun                    # 确保 core 运行(不在则拉起, 在则直接返回)
sun stop               # 停止 core
sun help               # 显示帮助和模块列表
sun <role>             # 调用模块的 run(); name 也可作为别名
sun <role> <子命令>     # 调用模块 subcommands 中登记的方法
```

`core` 只在第一次 `sun` 时自动拉起；之后一直常驻。`core` 退出后，下一次 `sun` 会重新拉起它。

---

## 二、目录规范

```text
modules/
└── mymodule/
    ├── mymodule.py      # core 唯一加载目标
    ├── mymodule.json    # 与 py 同名的市场元数据; core 读取 ID
    └── assets/          # 模块自己的资源, core 不加载
```

规则：

- core 只扫描 `modules/*/` 这一层目录。
- 只加载 `modules/<目录名>/<目录名>.py`。
- 同目录下的其他文件不会自动加载。
- 如果模块需要同目录的辅助 `.py`，可以用项目根作为路标导入，例如：

```python
from modules.mymodule import helper
```

core 以项目根为启动目录，项目根在 `sys.path` 中，所以这种导入方式可用。

- 目标文件固定导出名为 `Module` 的类：

```python
class Module:
    ...
```

core 只认 `Module`，不再用 `inspect` 猜“第一个类”。

## 三、最小模块

```python
class Module:
    role = "mymodule"                 # 主键, 必填, 非空字符串
    name = "mymodule"                 # 可选别名; 省略时等于 role
    desc = "一句话描述"                # sun help 显示
    used = True                       # 是否出现在 sun help / 允许 sun <role> 调用
    subcommands = ["status", "help"]  # 可通过 CLI 调用的子命令(list[str])

    def call(self):
        """一次性初始化: 可以调整 G.MODULES_LIST 顺序"""
        pass

    def run(self):
        """sun mymodule: 无子命令时调用"""
        print("mymodule run")

    def status(self):
        """sun mymodule status: 子命令"""
        print("ok")

    def help(self):
        """sun mymodule help"""
        print(self.desc)
```

ID 不写在类里，放在同目录与模块同名的 `mymodule.json`：

```json
{
    "name": "mymodule",
    "role": "mymodule",
    "desc": "一句话描述",
    "ID": "mymodule1792906494",
    "used": true,
    "need": []
}
```

### 生命周期

1. core 扫描模块目录，按目录名排序。
2. 读取每个模块的同名 `<名字>.json`，拿到 `ID`。
3. 导入目标文件，实例化名为 `Module` 的类。
4. 发现同 role 模块时，用 `ID` 里的时间戳比较，大的替换旧的。
5. 依次调用所有模块的 `call()`。
6. 进入命令循环。

注意：

- `Module` 必须是类，构造函数必须无参。
- `role` **必填**，必须是非空字符串。
- `name` 是可选的 CLI 别名；省略时等于 `role`。
- `used` 可选，默认 `True`。可以写在模块类里，也可以写在 `<名字>.json` 的 `used` 字段；JSON 优先。设为 `False` 时，模块仍会加载和初始化，其他模块也能通过 `G.get()` / `G.<token>` 访问，但它不会出现在 `sun help` 里，也不能用 `sun <role>` 调用。
- `desc`、`subcommands` 可以省略，core 会使用默认值。
- `call()` 是可选的，只会在 core 启动时调用一次。
- `call()` 里可以调整 `G.MODULES_LIST` 顺序，也可以追加全新模块实例；core 会把新实例继续排入 `call()` 队列。
- `call()` 抛异常：模块被移出列表。
- `call()` **不能阻塞**，否则 core 永远无法开始接收命令。
- `call()` 按 `G.MODULES_LIST` 顺序串行执行；如果模块之间存在初始化依赖，需要自己保证顺序，或改为惰性初始化。
- `load()` / `start()` 不再由 core 调用，这两个名字已经空出来，可以当作普通方法名或子命令使用。
- 模块只在 core 启动时初始化一次。改完代码后需要重启 core。

重启方式：

```bash
sun stop
sun <role> ...
```

## 四、命令路由

```bash
sun mymodule                 # 调用 run()
sun mymodule status          # 调用 status()
sun mymodule status a b      # 调用 status("a", "b")
```

规则：

- `run` 只在**没有子命令**时调用，不要在 `run` 里堆子命令解析。
- 每个子命令写成一个同名方法，并登记到 `subcommands` 列表。
- 只有 `subcommands` 中登记的方法可以通过 CLI 调用。
- `run` 是默认入口，不需要放进 `subcommands`。
- core 加载时会校验列表：不存在或不可调用的名字会跳过。
- 子命令不存在时直接报错，并列出当前可用子命令，不会回退到 `run`。
- 方法返回值不会自动打印；需要输出时使用 `print()`。

示例：

```python
class Module:
    role = "mymodule"
    name = "mymodule"
    subcommands = ["status", "help"]

    def run(self):
        print("default")

    def status(self):
        print("ok")

    def help(self):
        print("help")
```

```bash
sun mymodule                 # run()
sun mymodule status          # status()
sun mymodule status a b      # status("a", "b")
sun mymodule nope            # 报错, 并列出可用子命令
```

### `sun example help` 的穿透过程

1. `sun` 客户端把参数原样发给 core：`["example", "help"]`
2. core 用第一个参数 `example` 查 `name` / `role`
3. 找到模块后，把剩余参数 `["help"]` 当作子命令
4. 检查 `"help"` 是否在模块的 `subcommands` 列表里
5. 通过后调用 `getattr(module, "help")()`，也就是 `module.help()`
6. `print()` 的输出被 core 捕获，随响应返回给 `sun`

注意区分：

```bash
sun help            # core 内建帮助
sun example help    # 穿透给 example 模块的 help() 方法
```

`help` 是 core 内建命令，只输出全局帮助和模块列表，不接受模块名参数；同 role 模块无法覆盖它。

`list` 已释放，不再由 core 占用；模块可以把它作为普通子命令：

```bash
sun mymodule list
```

### help 输出约定

`sun help` 负责列出所有模块及其可用指令。输出内容约定为：

1. 模块的 `desc`：一句话说明这个模块有什么用；
2. `run()` 的 docstring 第一行：不传子命令时执行什么；
3. 每个 `subcommands` 成员的 docstring 第一行：这个子命令做什么、参数怎么传。

因此 docstring 的第一行要写成“作用 + 参数”，例如：

```python
class Module:
    role = "market"
    desc = "本地模块市场"

    def run(self):
        """打开模块市场面板"""

    def search(self):
        """搜索模块; 用法: sun market search <关键字>"""

    def install(self):
        """安装模块; 用法: sun market install <名字>"""
```

对应输出：

```text
market
  本地模块市场
  默认: sun market  - 打开模块市场面板
  子命令:
    sun market search ...  - 搜索模块; 用法: sun market search <关键字>
    sun market install ... - 安装模块; 用法: sun market install <名字>
```

## 五、G 与 T

core 在导入模块文件之前，会把 `G`、`T` 注入模块的全局命名空间：

```python
def call(self):
    print(G.APP_PATH)
    print(T.CLIENT_CWD)
```

不要写 `class Module(G, T)`，也不要 `from core import G`。它们是注入的实例，不是基类。

### G：全局共享对象

| 属性/方法 | 说明 |
| --- | --- |
| `G.APP_PATH` | 项目根目录 |
| `G.MODULES_LIST` | 当前模块实例列表，顺序就是初始化顺序 |
| `G.by_name` | `name -> 模块实例` 别名索引 |
| `G.by_role` | `role -> 模块实例` 主键索引 |
| `G.get(name)` | 按 role 或 name 取模块，找不到返回 `None`；role 优先 |
| `G.log(message, path="")` | 追加一条带时间戳的日志；`path` 为空时写入 `./log/sun.log` |
| `G.<name>` / `G.<role>` | 自动挂载的模块属性，前提是名字是合法标识符且不与 core 保留名冲突 |

查找顺序是 **role 优先，name 兜底**。模块间取实例时优先用 `G.get("xxx")` 或 `G.xxx`，不要直接依赖 `G.by_name` / `G.by_role` 处理冲突。

`G.log` 的第二个参数可以是绝对路径，也可以是相对项目根目录的路径：

```python
G.log("mymodule 启动完成")                    # 写入 ./log/sun.log
G.log("下载失败", "log/download.log")          # 写入项目根下的 log/download.log
G.log("使用绝对路径", "/tmp/mymodule.log")     # 写入指定文件
```

写入格式为：

```text
[2026-10-25 14:30:00] mymodule 启动完成
```

不要假设某个模块一定存在。插件之间应该是可选依赖。

### T：请求上下文

| 属性 | 说明 |
| --- | --- |
| `T.CLIENT_CWD` | 本次 `sun` 调用时用户所在目录 |

`T` 只用于临时上下文，不要在里面保存跨请求的长期状态。

## 六、name、role 与 ID

### role

- **主键，必填，非空字符串**。
- 不支持列表、`None` 或空字符串。
- 未设置 `role` 的模块会被丢弃。
- 例如：

```python
role = "log"
name = "mylog"    # 可选别名
```

这样 `sun log` 是主命令，`sun mylog` 也能命中。

### name

- 可选的 CLI 别名。
- 省略或为空时自动使用 `role`。
- 查找顺序：先查 `role`，没有命中才查 `name`。

### used

- 可选布尔值，默认 `True`。
- 可以写在模块类里（`used = True/False`），也可以写在 `<名字>.json` 里（`"used": true/false`）；JSON 优先。
- `used = True`：模块出现在 `sun help`，并允许 `sun <role>` 调用。
- `used = False`：模块仍然加载、仍然执行 `call()`，其他模块仍可通过 `G.get()` / `G.<token>` 使用它，但它不会出现在 `sun help`，`sun <role>` 会提示“未开放给 sun”。
- `used` 只控制 CLI 暴露，不影响初始化顺序和模块间访问。
- 如果模块需要一个叫 `used` 的子命令（例如 `market used`），不要在类里声明 `used` 布尔属性，改用 `<名字>.json` 的 `"used"` 字段。core 内部最终状态保存在 `_used`。

### ID

- ID 写在同目录的 `<名字>.json` 里，由 market 分配。
- 格式：`name + str(int(time.time()))`，例如：

```json
{"ID": "myplugin1792906494"}
```

- core 读取 manifest 后，去掉 `name` / `role` 前缀，把剩余数字按整数比较。
- 发现同 role 模块时，ID 时间戳大的直接替换旧的。
- 没有 ID 或数字解析失败时视为最小；同 role 且时间戳不更大时保留旧模块。
- 不需要 `priority` 字段。

## 七、`<名字>.json`

`modules/<名字>/<名字>.json` 是市场/开发者元数据。core 会读取 `ID`、`used` 和 `desc`（`desc` 缺失时用 `help` 兜底），其余字段不由 core 使用。

示例：

```json
{
    "name": "mymodule",
    "role": "mymodule",
    "desc": "一句话描述",
    "ID": "mymodule1792906494",
    "used": true,
    "api": ["run", "status"],
    "need": []
}
```

说明：

- `ID` 用于同 role 模块的时间戳比较和替换。
- `used` 控制是否出现在 `sun help`、是否允许 `sun <role>` 调用；JSON 优先于类属性。
- `desc` 可作为模块 `desc` 的兜底；`help` 是兼容旧字段。
- `api` 已废弃；core 的 CLI 路由使用模块类属性 `subcommands`。
- `need` 只是文档/市场依赖声明，core 不据此排序；需要顺序时在 `call()` 里调整 `G.MODULES_LIST`。
- 模块需要读取自己的完整配置时，自己读：

```python
import json
from pathlib import Path

cfg = json.loads(Path(__file__).with_suffix(".json").read_text("utf-8"))
```

## 八、输出、日志与错误

### 输出

`print()` 会被 core 捕获，并随命令结果返回给 `sun`：

```python
def status(self):
    print("ok")
```

后台线程里的 `print()` 不保证能被当前请求捕获，长期运行的服务应写日志或走自己的控制通道。

### 日志

core 不再写常规日志，只处理致命错误：

- 写一条 fatal-only 记录到 `core/core.log`
- 调用系统消息弹窗：Windows `MessageBox`、macOS `osascript`、Linux `zenity` / `kdialog` / `notify-send`
- 没有可用 GUI 工具时回退到 stderr

模块自己的常规输出用 `print()`；需要写日志时直接用 core 提供的 `G.log`：

```python
G.log("mymodule: something happened")
G.log("mymodule: 写入自定义文件", "log/mymodule.log")
```

默认写入项目根目录下的 `log/sun.log`。`G.log` 会自动创建父目录，并按追加方式写入。

### 错误

- 未知模块 / 未知子命令：返回错误，退出码 2。
- 模块方法抛异常：core 把 traceback 返回给 `sun`，退出码 1。
- `call()` 失败：模块被移出列表。
- core 自身无法继续运行：fatal 日志 + 系统弹窗。

## 九、长任务与常驻服务

core 是**单线程、串行**处理命令的：

- `call()` 必须快速返回。
- `run()` 或子命令如果阻塞，会挡住其他所有 `sun` 命令。
- 长任务请自己开线程/进程，或提供自己的控制通道。
- core 不管理服务 PID、不自动重启服务；这些由模块自己负责。

推荐模式：

```text
模块 call()
  → 启动自己的后台线程/进程
  → 立即返回

模块 stop()
  → 通过自己的控制通道通知后台任务退出
```

如果模块需要接收运行时指令，使用自己的控制通道（socket、队列、文件等），不要依赖 core 的 stdin/stdout。

## 十、路径与工作目录

- core 常驻在项目根目录。
- core 只在 `core/` 目录维护 `core.sock` / `core.pid` / `core.lock` / `core.log`，不使用 `data/`、`config/` 目录。
- `G.log` 默认写入项目根目录下的 `log/sun.log`，会自动创建 `log/`。
- 模块需要持久化目录时自己创建；相对路径仍相对于项目根。
- 需要用户当前目录时，用 `T.CLIENT_CWD`。
- 需要项目根时，用 `G.APP_PATH`。

```python
from pathlib import Path

project_root = Path(G.APP_PATH)
caller_dir = Path(T.CLIENT_CWD)
```

## 十一、调试

```bash
sun                       # 确保 core 运行
sun stop                  # 停止 core
sun help                  # 看模块有没有加载
tail -f core/core.log     # 只看致命错误
tail -f log/sun.log       # 看 G.log 写入的模块日志
sun <role> ...            # 下一次会自动拉起 core
```

模块没出现时，按顺序检查：

1. 目录是否是 `modules/<名字>/<名字>.py`；
2. 目标文件是否导出了名为 `Module` 的类；
3. `call()` 是否抛异常（失败模块会被静默移除）；
4. `call()` 是否把自己从 `G.MODULES_LIST` 移除了；
5. `used` 是否被设成了 `False`；
6. core 是否需要重启（代码只在启动时加载一次）。

## 十二、注意事项

1. **不要继承 G/T**，它们是注入实例。
2. **不要 `from core import G`**，core 不会把模块文件当包导入。
3. **不要在 `run()` 里堆子命令解析**，子命令写成同名方法并登记到 `subcommands`。
4. **`role` 必填且是非空字符串**；`name` 只是可选别名；两者都不能是 `help` / `stop`。
5. **不要假设其他模块存在**，用 `getattr(G, "...", None)`。
6. **不要在 `call()` 里阻塞**。
7. **同目录的辅助文件不会被自动加载**，需要模块自己处理。
8. **`<名字>.json` 的 `ID` 由 core 用于同 role 替换；`need` 不由 core 使用**。
9. **模块只初始化一次**，改代码后重启 core。
10. **`help` / `stop` 是 core 保留命令**；`list` 已释放，模块可以正常使用。
11. **core 当前是 Linux 优先的 UDS 实现**；插件不需要关心传输层，但跨平台运行 core 前需要确认目标系统支持。
12. **core 只对致命错误弹系统消息**；模块加载/初始化失败会被静默移除，调试时先检查代码和 `<名字>.json`。
13. **辅助文件用 `from modules.<目录名> import <模块>` 导入**，不要依赖模块目录被加入 `sys.path`。
14. **`call()` 里可以追加全新模块实例**，core 会继续执行它们的 `call()`。
15. **`load()` / `start()` 不再有生命周期含义**，core 不会调用它们；需要隐藏模块请设 `used = False`。

## 十三、market / market_manager 模块

`market` 是随项目仓库分发的用户版，负责查询、安装和本地管理：

```bash
sun market list                 # 列出已安装模块
sun market find <关键词>        # 搜索共享 Release
sun market install <name/ID>    # 安装或更新模块
sun market mkid <name/ID>       # 生成或更新 ID
sun market used <name/ID>       # 启用模块
sun market unused <name/ID>     # 弃用模块
sun market rm <name/ID>         # 删除本地模块目录
```

`market_manager` 是开发者工具，在 `market` 的基础上增加云端写操作：

```bash
sun market_manager upload <name/ID>   # 上传模块 zip
sun market_manager delete <name/ID>   # 删除云端模块(需确认)
```

`market_manager` 默认不随仓库分发，已加入 `.gitignore`；它作为独立模块运行，`name` 是 `market_manager`，`role` 与 `market` 相同，都是 `market`。

### 配置

`modules/market/market.json`：

```json
{
    "gitee": {
        "repo": "xiuufa/sunday",
        "release_tag": "mods",
        "index_asset": "index.json"
    }
}
```

`modules/market_manager/market_manager.json` 额外支持 `token`、`release_name`、`target_commitish`：

```json
{
    "gitee": {
        "repo": "xiuufa/sunday",
        "token": "",
        "release_tag": "mods",
        "release_name": "Sunday modules",
        "target_commitish": "master",
        "index_asset": "index.json"
    }
}
```

- `repo` 写 `owner/repo`，也可以直接写 Gitee 地址。
- download 读取公开仓库，不需要 token。
- upload / delete 需要 token：`GITEE_TOKEN` 环境变量、`env:GITEE_TOKEN`、直接填 `gitee.token`，或保存到 `~/.config/sunday/gitee_token`。
- 不要把真实 token 提交到仓库。
- `target_commitish` 是创建 Release 时使用的分支，默认 `master`。

### 共享 Release

- 所有模块共用一个 Gitee Release：`tag = mods`。
- 每个版本保存为 `<ID>.zip`，旧版本不删除。
- 额外维护一个 `index.json`，记录所有版本的 `name`、`role`、`ID`、`desc`、`asset`、`download_url`。
- `find` 只读取 `index.json`，不会下载所有 zip。
- 同 `name` 在展示时只显示最新 ID，但云端保留所有版本。
- 同一个 ID 不允许重复上传；需要新版本时先 `sun market mkid <name>`。
- `find` / `install` 会把 `index.json` 缓存到项目根目录 `tmp/index.json`；该目录由 market 在启动时清空。

### 行为

- `list` 扫描 `modules/*/`，读取每个模块的 JSON 和已加载实例，同 `name` 只显示最新 ID。
- `find` 在 `index.json` 中按 `name`、`role`、`ID`、`desc` 做大小写不敏感匹配，同 `name` 只显示最新；云端失败时可回退到本地缓存。
- `install` 按 name 或 ID 从 Gitee Release 下载 zip，校验包内 `name`、`ID` 和路径后安装到 `modules/<name>/`；已存在时先备份再替换。要移除的旧 ID 不在云端时，客户端会要求回车确认；也可以直接加 `--yes`。
- `mkid` 写入 `<name><int(time.time())>`；重启 core 后参与同 role 替换。
- `upload`（仅 market_manager）检查 ID 必须是 `<name><数字>`，并拒绝云端已存在的同 ID；打包整个模块目录，并清空 market_manager 自身 zip 里的 token。
- `delete`（仅 market_manager）按 ID 精确删除；传入 name 时删除该 name 的全部云端版本。删除 zip 资产并重写 `index.json`，执行前需要回车确认。
- `used` / `unused` 写入目标模块 JSON 的 `used` 字段；已加载模块会立即同步，重启后依然保持。
- `rm` 删除目标模块目录，并从当前 core 的 `G.MODULES_LIST` 和索引中移除。
